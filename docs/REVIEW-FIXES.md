# レビュー指摘の修正と適用手順

## 変更点

| 指摘 | 修正 |
|---|---|
| HTTPの子プロセスが継続する保証がない | 関数を直接awaitする。import時に実行しない。実行ごとの状態と通信期限を分離 |
| 定期起動なし | 認証付きCronを追加。未設定・短い秘密値は拒否。middlewareからログインに転送しない |
| 記録係の二重実行 | DB行ロックで取り込み権を取得。所有トークンで古い実行の書き込みを拒否 |
| 自己分析の巨大入力・連打 | ストリーム読み取りで全体4MB。2〜12枚、512KB/枚、1920×1080以内。デコード検査。5分間隔・10回/24時間・本人ごと同時1回 |
| 費用が呼び出し後に上限超過 | 呼び出し前の費用見積りと25%の余裕、max_tokens、費用不明なら追加呼び出し停止。READMEの請求保証を訂正 |
| ライブと作成者登録の途中失敗 | 1トランザクションのRPC |
| 幹事の二重起動 | 全入口共通の部分ユニーク制約。Cronの日付単位の重複も排除 |
| 記録係の部分書き込み・復旧不能 | 成果物と完了記録を1トランザクションで確定。途中失敗をロールバック。リース切れを再取得。最大3回で要確認 |

元のZIPにあるDESIGNには「今回はCron未設定」と書かれていた。レビューで示された設計書の版とは差があった。今回の修正では日次起動もコードとして追加した。

## 適用順

1. このZIPの内容を作業リポジトリへ反映する。自分の `.env.local` は保持する。
2. 旧コードのCLI、ループ、HTTPからのエージェント実行を止める。**旧版と新版を同時稼働させない。**
3. DBバックアップ後、既存の `0001`〜`0014` が適用済みであることを確認し `supabase/migrations/0015_agent_safety.sql` をSQL Editorで適用する。古いファイルを一括再実行しない。
4. `npm ci` → `npm test` → `npm run build`。ローカル起動は `npm run dev`。
5. 本番環境に既存のサーバー用環境変数と **`CRON_SECRET`（16文字以上のランダム文字列）** を設定する。ブラウザ公開変数にしない。
6. ホスティングで300秒のFunctions実行時間が使える設定を確認して新コードをデプロイする。コードは通信を240秒で止める。稼働後に管理者起動・Cron・実際のライブ終了を確認する。
7. OrcaRouter側で各キーの予算と上限超過時の拒否を確認する。これはこちらのコードやローカルテストでは確認できない。

この作業では本番DB・外部API・デプロイ先の設定を変更していない。

## Cron

| パス | UTC | 日本時間 | 動作 |
|---|---|---|---|
| `/api/cron/organizer` | 00:00 | 09:00 | 幹事1周。同一UTC日の再配信はスキップ |
| `/api/cron/recorder` | 00:30 | 09:30 | 終了ライブの未処理・リース期限切れを1件処理 |

手動起動も定期起動も同じDBの排他を通る。Cronを呼ぶときは `Authorization: Bearer <設定した値>` が必要。
日次の復旧は大量のバックログ処理用ではない。通常はライブ終了APIで即時処理する。バックログが多い場合は管理者が該当ライブの終了APIを再実行するか、ジョブキューへ移行する。
Cronの失敗を同日自動で無制限に再実行しない。Bが失敗した日は実行記録を確認して手動で再実行する。

## 復旧

- **新版A**: 通常の失敗は書き込みが全て戻り `pending` に戻る。3回失敗すると `needs_review`。強制終了でも10分後にCronまたは同じライブ終了APIで再取得できる。応答だけ失われたコミットは `done` が残るため再加算されない。
- **旧版Aのrunning**: 既に一部のタグが増えている可能性があり、自動リプレイしない。移行で `needs_review` にする。カード・タグ強度・tag_mentionsを確認してから個別に修復する。
- **B/Cのrunningが残る場合**: 新しい実行を拒否する。時刻だけでロック解除すると旧プロセスとの二重書き込みになり得る。実プロセスが停止したことと副作用を確認してからSQL Editorで該当runだけを失敗として閉じる。例のIDは確認した実行IDに置き換える。

```sql
update public.agent_runs
set status = 'failed', finished_at = now(), error = 'operator confirmed worker stopped'
where id = <確認した実行ID> and status = 'running' and agent in ('B','C');
```

移行時にBやCの重複runningが残っていればユニーク制約の作成が失敗し、移行全体が戻る。勝手に成功扱いにせず同様に調査してから再適用する。
Aの `needs_review` を再処理する場合も原因と旧版の残存データを確認する。新版の失敗で成果物が無いと確認できた場合のみ `ingest_status='pending', ingest_attempts=0, ingest_token=null, ingest_lease_until=null` に戻す。

## 費用の設定

Bの既定値は停止目安 `$1`、見積入力単価 `$10/百万トークン`、出力単価 `$50/百万トークン`。
`ORGANIZER_BUDGET_USD` / `ORGANIZER_INPUT_USD_PER_MILLION` / `ORGANIZER_OUTPUT_USD_PER_MILLION` で変更できる。正の有限数以外は拒否する。
入力はUTF-8バイト数を保守的なトークン数の目安とする。最大出力2048トークン分も予約する。単価は実際にルーターが選べるモデルに合わせる。
**推定には誤差があり外部ルーターの価格変更もあるため請求上限の保証ではない。**

## 検証の範囲

- `npm test`: PGlite（PostgreSQLのWASM版）に実際のスキーマ・RLS・追加マイグレーションを適用。排他制約、Cron重複、利用回数、RPC権限、途中失敗の全体ロールバック、取り込み再実行・古い所有トークンの拒否を検査。
- Nodeテスト: Content-Lengthなしの巨大リクエスト、実画像のデコード・MIME・枚数・解像度、Cron認証、費用設定を検査。
- ビルドで全Routeとサーバー境界を確認。15件のテストが成功。
- 本番用ビルドのローカル起動で2つのCron RouteをHTTP確認。認証なしは401で拒否し、ログイン画面へ転送しない。
- PGliteは単一接続のため、本番の複数DB接続での競合負荷テストの代わりではない。実APIキーを使うLLM疎通・本番Cron・デプロイ・実データ移行は未実施。

プロンプトは `lib/agents/prompts/*.md` を編集し `npm run prompts` でモジュール化する。ビルド時も自動生成するためサーバーレス成果物からプロンプトが欠けない。
