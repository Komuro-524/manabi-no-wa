# 0010 適用後の検証（anonキー・実ログイン）

記録日時: 2026-09-21 昼過ぎ

`supabase/migrations/0010_hide_growing_content.sql` を適用したあと、
`NEXT_PUBLIC_SUPABASE_ANON_KEY` で実際に架空社員としてログインし、
service_roleを経由せず本当にRLSだけで守られているかを確認した。
（パスワードは `0006_demo_seed.sql` の全社員共通のダミー値）

## (a) 一般社員として見えるカード

依頼では「早坂 悠人」を一般社員の代表として指定されていたが、確認したところ
**早坂悠人はまさに候補・格上げ候補タグのカード#21・#22・#24を自分で話した人**だった
（F3/タグ昇格の検証で作ったデータのため）。そこで2人分を記録する。

### 早坂 悠人（自分の候補/格上げ候補カードを持つ人としての参考値）

```
見えるカード合計=13 / 正式タグのカード=10 / 候補・格上げ候補タグのカード=3
内訳: #21・#22（インデックス/proposed）・#24（実行計画/proposed） ← 全部「自分が話した」カード
```

他の人が話した候補・格上げ候補カード（例: #27 実行計画/proposed, 神谷美月が話した）は
**見えていない**。「自分の分だけ見える」が正しく効いている。

### 星野 陸（候補・格上げ候補タグのカードを一度も話していない、純粋な一般社員）

```
見えるカード合計=10 / 正式タグのカード=10 / 候補・格上げ候補タグのカード=0
```

こちらが依頼どおりの「0件」。**一般社員は他人の候補・格上げ候補カードを一切見られない**
ことを確認できた。

## (b) 話した本人：自分の候補・格上げ候補カードは見える

```
早坂悠人としてログインし、#21・#22・#24 をidで直接select
→ 3件とも取得できた（{id:21,...}{id:22,...}{id:24,...}）
```

id指定でも取れる＝RLSのselectポリシー自体が「自分の分は通す」形になっている
（一覧に出るかどうかの見た目の話ではなく、行レベルで保証されている）。

⚠️ 気づいたこと（別件・今回は対応しない）: この時、埋め込みの `tags(name,status)` は
`null` で返ってきた。これは `knowledge_cards` は本人の行として見えるが、
`tags` テーブル自体のRLS（「正式タグは全員 それ以外は管理者」）により、
**候補・格上げ候補タグの行そのものは非管理者からは（自分のカードに付いていても）読めない**ため。
画面（`cards`画面）で「自分の育ちかけカードにタグ名を出す」実装をするときは、
クライアント側の直接joinではなく **サーバー側（service_role）でタグ名を解決して渡す**
必要がある。`docs/QUESTIONS.md`に記録する。

## (c) 管理者（松永 蒼）：全部見える

```
見えるカード合計=14 / 正式タグのカード=10 / 候補・格上げ候補タグのカード=4
内訳: #21(インデックス/proposed) #22(インデックス/proposed) #24(実行計画/proposed) #27(実行計画/proposed)
見えるuser_tags合計=38 件（エラー無し）
```

一般社員（早坂・星野）には見えなかった #27（神谷美月の実行計画カード）も含めて
**候補・格上げ候補すべてが見えている**。`is_admin()` 経由のバイパスが機能している。

## (d) 参加していないライブにチャットを書こうとして拒否される

live#18（参加者: 星野陸・郡司蓮）を検証のため一時的に `status='live'` にし
（**参加者チェック単体を確認するため**。free/busy等には触れていない）、
参加者ではない早坂悠人でログインして投稿を試みた。

```
insert結果 error: 42501 new row violates row-level security policy for table "messages"
```

拒否された。検証後、live#18は `status='ended'` に戻し、`messages`に行が残っていない
（0件）ことも確認した。

## (e) 終わったライブにチャットを書こうとして拒否される

live#17（`status='ended'`。星野陸は本来の参加者）で、**正規の参加者である星野陸**が
投稿を試みても拒否されることを確認した。

```
insert結果 error: 42501 new row violates row-level security policy for table "messages"
```

参加者であっても、ライブが終了していれば書けない（F5の`lives.status='live'`条件が
効いている。参加者チェックだけでなく状態チェックも独立して機能している）。
