# F9: フォールバックを実際に起こす

記録日時: 2026-09-21 昼過ぎ（1回目の失敗）／同日 続報（2段構えに直したあと）

## やったこと

```
ORCA_FORCE_FALLBACK=1 node scripts/recorder.mjs --live 18 --dry
```

`scripts/recorder.mjs`は`ORCA_FORCE_FALLBACK=1`のとき、第1候補を存在しないモデル
`openai/this-model-does-not-exist`にし、`models: [BROKEN_MODEL, MODEL], route: 'fallback'`
（`MODEL`は`orcarouter/manabi-recorder`というNamed Routerのエイリアス）を付けて呼ぶ実装になっている。

## 結果（そのまま貼り付け。手を加えていない）

```
🎙️ ライブ #18 まなびのライブ「DX推進担当が集まる社内勉強会」F7検証回 — 費用の突き合わせ用の短い回
   発言 2行 / チャット 0件 / 参加者 2人

🧨 ORCA_FORCE_FALLBACK=1: 第1候補を存在しないモデル（openai/this-model-does-not-exist）にして呼びます

   表記を揃える参考に渡すタグ: 正式13件 / 育ちかけ35件
   1個の塊に分割

🧠 抽出中...

🛑 失敗: 404 No available capacity for model openai/this-model-does-not-exist right now. Please try again later. Models you can call: https://www.orcarouter.ai/console/models?ref=err_model_unknown (request id: 202609210640199215046068268d9d6CanfL7er)
```

**フォールバックは発動しなかった。** `models`配列に`orcarouter/manabi-recorder`という
Named Routerのエイリアスを2番目の候補として入れても、OrcaRouterは存在しない1番目のモデルで
即座に404を返し、2番目へは切り替わらなかった。

## 副次的な確認

- `--dry`実行だったため、DBへの副作用は無い（`agent_runs`行は作られず、`lives.ingest_status`も
  変わっていない。失敗はLLM呼び出しの中で起きたため、コスト面の実害も無い＝$0）

## 指示どおり、モデル名は差し替えていない

依頼にあった「modelsにルーター名を入れて動かなかった場合は、エラー文をそのまま記録して止まり報告
（勝手にモデル名へ差し替えない）」に従い、`BROKEN_MODEL`を実在のデフォルトモデル名に
書き換えるなどの修正は行っていない。`scripts/recorder.mjs`は依頼どおりCowork側の実装のまま。

## 考えられる原因（推測。検証はしていない）

- `route: 'fallback'`の仕様上、`models`配列には**実在するモデルID**だけを想定しており、
  Named Routerのエイリアス（`orcarouter/manabi-recorder`）を2番目の候補として渡すこと自体が
  サポート外の可能性がある
- あるいは、1番目のモデルが「存在しない」（`err_model_unknown`）という**リクエストの検証エラー**
  として扱われ、その時点でリクエスト全体が拒否され、`route: 'fallback'`によるモデル間の
  フェイルオーバーの土俵にすら乗っていない可能性がある（フォールバックは「呼べたが失敗した」
  ときの仕組みで、「そもそも存在しないモデル名を書いた」場合は別扱いかもしれない）

この時点では対応（コードの修正）は行っていない。判断は持ち帰りとした。

## 続報: 受け皿を2段にしたあと（Cowork側で修正・確認済み）

`scripts/recorder.mjs`が直った。OrcaRouter自体の`route: 'fallback'`（1段目）に加えて、
**呼び出しが例外で落ちたら（404・429・5xx・通信断など）アプリ側でもう一度だけ
別ベンダーのモデルを直接呼ぶ**（2段目）実装になった。
`ORCA_FORCE_FALLBACK`で2パターンを切り替えて確認した。

### 1) `ORCA_FORCE_FALLBACK=orca`（1段目のOrcaRouterフォールバックを試す）

```
ORCA_FORCE_FALLBACK=orca node scripts/recorder.mjs --live 18 --dry

🧠 抽出中...
  🔁 塊1: 1回目が失敗（404: 404 No available capacity for model openai/this-model-does-not-exist right now. ）→ 受け皿 google/gemini-2.5-flash-lite で1回だけやり直す
  塊1: ? / $0.00021

カード候補 0件 / 興味 0件 / アンコール 0回
🚪門1の結果: 貼る 0件（なし） / 落ちた 0件
🧪 --dry なのでDBには書きません
```

**1段目（OrcaRouterの`route:'fallback'`）は前回と同じく404で失敗したが、
2段目（アプリ側の受け皿）が拾って`google/gemini-2.5-flash-lite`で最後まで成功した。**
「🔁 …→ 受け皿 … で1回だけやり直す」の行が出て、処理は正常終了している
（`--dry`のためDB書き込みは無し。この文字起こしは雑談のみなのでカード・興味は0件が正しい）。

### 2) `ORCA_FORCE_FALLBACK=app`（最初からアプリ側の受け皿だけを試す）

```
ORCA_FORCE_FALLBACK=app node scripts/recorder.mjs --live 18 --dry

  塊1: ? / $0.00021

カード候補 0件 / 興味 0件 / アンコール 0回
🚪門1の結果: 貼る 0件（なし） / 落ちた 0件
🧪 --dry なのでDBには書きません
```

こちらも同じく「🔁 …受け皿…で1回だけやり直す」が出て、`google/gemini-2.5-flash-lite`で
最後まで成功した。

### まとめ

| 試したこと | 1段目(OrcaRouter route:fallback) | 2段目(アプリ側の受け皿) | 最終結果 |
|---|---|---|---|
| `ORCA_FORCE_FALLBACK=orca` | 404で失敗（前回と同じ） | 発動・成功 | ✅最後まで成功 |
| `ORCA_FORCE_FALLBACK=app` | （最初からアプリ側狙い） | 発動・成功 | ✅最後まで成功 |

1段目（OrcaRouter自体のモデル間フォールバック）は今回もこの構成では発動しなかったが、
**2段目のアプリ側の受け皿が両方のケースを拾い、処理は2回とも最後まで成功した。**
「受け皿を用意していたが一度も発動していなかった」という当初の課題は解消され、
実際に発動・成功する様子を確認できた。
