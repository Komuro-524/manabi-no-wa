# F9: フォールバックを実際に起こす（結果: 動かなかった）

記録日時: 2026-09-21 昼過ぎ

## やったこと

```
ORCA_FORCE_FALLBACK=1 node scripts/recorder.mjs --live 18 --dry
```

`scripts/recorder.mjs`は`ORCA_FORCE_FALLBACK=1`のとき、第1候補を存在しないモデル
`openai/this-model-does-not-exist`にし、`models: [BROKEN_MODEL, MODEL], route: 'fallback'`
（`MODEL`は`orcarouter/manabi-recorder`というNamed Routerのエイリアス）を付けて呼ぶ実装になっている。

## 結果（そのまま貼り付け。手を加えていない）

```

   発言 2行 / チャット 0件 / 参加者 2人

```

**フォールバックは発動しなかった。** `models`配列に`orcarouter/manabi-recorder`という
Named Routerのエイリアスを2番目の候補として入れても、OrcaRouterは存在しない1番目のモデルで
即座に404を返し、2番目へは切り替わらなかった。

## 副次的な確認

- `--dry`実行だったため、DBへの副作用は無い（`agent_runs`行は作られず、`lives.ingest_status`も
  変わっていない。失敗はLLM呼び出しの中で起きたため、コスト面の実害も無い＝$0）

## 指示どおり、モデル名は差し替えていない

依頼にあった「modelsにルーター名を入れて動かなかった場合は、エラー文をそのまま記録して止まり報告
（勝手にモデル名へ差し替えない）」に従い、`BROKEN_MODEL`を実在のデフォルトモデル名に
書き換えるなどの修正は行っていない。`scripts/recorder.mjs`は依頼どおりCowork側の実装のまま。

## 考えられる原因（推測。検証はしていない）

- `route: 'fallback'`の仕様上、`models`配列には**実在するモデルID**だけを想定しており、
  Named Routerのエイリアス（`orcarouter/manabi-recorder`）を2番目の候補として渡すこと自体が
  サポート外の可能性がある
- あるいは、1番目のモデルが「存在しない」（`err_model_unknown`）という**リクエストの検証エラー**
  として扱われ、その時点でリクエスト全体が拒否され、`route: 'fallback'`によるモデル間の
  フェイルオーバーの土俵にすら乗っていない可能性がある（フォールバックは「呼べたが失敗した」
  ときの仕組みで、「そもそも存在しないモデル名を書いた」場合は別扱いかもしれない）

対応（コードの修正）は行っていません。判断は持ち帰りです。
