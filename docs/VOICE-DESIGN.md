# 🎙️ 声の設計 — 今回のデモと 将来の音声通話

> 今回のデモは **ブラウザの音声入力で文字だけを共有** する。
> 本当に声を届ける音声通話は **この文書の構成で足せる** ように設計してある。
> 足すのは「声の通り道」だけで **文字起こしから先（`transcript_segments` → タグ付け → 知見カード）は一行も変えない**。

---

## 1. 今回のデモ（実装済み）

### 1.1 流れ

| # | どこで | 何が起きる |
|---|---|---|
| 1 | ライブ画面（話し手だけ・配信中だけ） | 「🎙️ マイクで話す」→ **同意の説明**（声の行き先・保存しない・評価に使わない）→ 同意して開始 |
| 2 | ブラウザ | Web Speech API（`ja-JP`・連続・途中経過あり）で文字にする。途中経過は **自分の画面だけ** に出す |
| 3 | ブラウザ → `POST /api/lives/[id]/segments` | **確定した一文だけ** を送る。声は送らない |
| 4 | サーバー | 認証サーバーで本人を確かめる（`getUser`）→ 配信中か → **このライブの話し手か** → `user_id` は **本人のもので固定**して `transcript_segments` に1行 |
| 5 | ライブ画面 | コメントと「🎙️ 話した言葉」を時刻順に並べる。参加者は数秒おきに読み直す |
| 6 | ライブ終了 | タグ付けエージェント（recorder）が **今までどおり** 文字起こし＋チャットを読む |

### 1.2 守っていること

| 心配 | 対策 |
|---|---|
| 他人の発言を作られる | `transcript_segments` に **ブラウザ向けの insert ポリシーは無い**。書けるのはサーバーだけ。ブラウザから `user_id` は受け取らない |
| 聞くだけの人・部外者が書く | サーバーで `live_participants.role = 'speaker'` と `lives.status = 'live'` を確かめる。外れたら 403 / 409 |
| 巨大な入力・連投 | 1回500文字まで。空白は詰める |
| 同時に確定して番号がぶつかる | `unique (live_id, seq)` にぶつかったら数え直して最大5回やり直す |
| 読めない人に見える | 読むのは既存の RLS（参加者だけ）のまま |

### 1.3 デモの限界（正直に）

| 限界 | 理由 |
|---|---|
| **声は他の参加者に届かない** | 文字だけの共有。音声通話は §2 |
| 声はブラウザの提供元（Chrome なら Google／Edge なら Microsoft）のサーバーで文字になる | Web Speech API の仕組み。だから開始前に同意を取る。**社内運用ではこの形は使わない**（§2 で社内完結に置き換える） |
| Chrome と Edge だけ | Firefox は未対応。非対応ブラウザには案内を出す |
| 社内プロキシが音声認識の通信を止めると使えない | 画面に「サーバーに届きません（社内ネットワークで止められている可能性）」と出す |

## 2. 将来の音声通話の構成

### 2.0 まず決めること — サーバーを「誰が」持つか（提供形態）

この文書で「サーバーを建てる場所」と言うときは、**次の2つの形のどちらか** を指す。
声だけでなく **まなびのわ全体（画面・DB・エージェント）も同じ場所に置く**。

| | 🅰️ 標準プラン（SaaS） | 🅱️ 専用環境プラン |
|---|---|---|
| 誰が建てて運用するか | **開発元（私たち）** | **導入企業（お客さん）** のクラウド。構築は私たちが手伝う |
| 置き場所 | 私たちの国内リージョンのクラウド | お客さんの Azure など（お客さんのテナント） |
| 使い始め | ✅ **契約した日から** | ❌ 構築に数週間〜 |
| 声と文字の通り道 | 私たちのサーバーを通る（国内で処理・録音なし・声は保存しない） | **お客さんの環境から出ない** |
| お客さんの安心材料 | 利用規約とデータ処理の約束・第三者認証・データの流れの図 | 自分の管理下にある |
| 向いている相手 | 中小〜中堅企業・まず試したい会社 | 金融・官公庁・大企業など 社外に声を出せない会社 |

> 💡 たとえ: 🅰️は **貸し会議室**（当日から使えるが管理人は私たち）、🅱️は **自社ビルに会議室を作る工事**（安心だが完成まで時間がかかる）。
> どちらでも **コードは同じ**。違うのは置き場所と、鍵を誰が持つかだけ。

**どちらのプランでも残る関門**（お客さんの会社側）

| 関門 | 中身 | 軽くする工夫 |
|---|---|---|
| 🌐 情シスの通信許可 | 許可リスト制の会社では まなびのわのドメインを許可してもらう | **443番だけで通る** 作りなので、依頼は「2ドメインの許可」と「TLS 復号の対象外」だけ（§4.1） |
| 📋 セキュリティ審査 | 大企業は導入前にチェックシートで審査する | 回答集・データの流れの図・「声は保存しない」の説明を **先に用意しておく** |

**機能ごとの「すぐ使えるか」**

| 機能 | 🅰️ 標準 | 🅱️ 専用 |
|---|---|---|
| 💬 チャット・知見カード・タグ・場づくり | ✅ すぐ | 構築後 |
| 🎙️ ブラウザ音声入力（今回のデモ） | 🟡 動くが 声がブラウザ提供元に行くので **お客さんの同意が要る** | 🟡 同じ |
| 📞 音声通話 | ✅ 通信許可だけで使える | 構築後 |

### 2.1 部品

| 部品 | 役割 | 候補 |
|---|---|---|
| 🎧 SFU（音声の中継サーバー） | 話し手の声を受けて 聞き手に配る。混ぜない・保存しない | **LiveKit**（OSS・自前で建てられる） |
| 🔑 トークン発行 API | 「この人が この部屋に この権限で入ってよい」を署名して渡す | まなびのわの `app/api/lives/[id]/token`（新規） |
| 📝 STT エージェント | 話し手ごとの音声トラックを購読して文字にする SFU と同じ場所に置く。🅰️は私たちの国内クラウド、🅱️はお客さんのテナント（Azure AI Speech の東日本リージョン＋プライベート接続）か 自前の Whisper |
| 🔔 Webhook 受け口 | 入室・退室・部屋の終了を受けて記録 | `app/api/voice/webhook`（新規・署名検証） |
| 🗂️ `transcript_segments` | **今と同じ**。`user_id` 付きで1行ずつ | 変更なし |
| 🎙️ recorder / 知見カード | **今と同じ** | 変更なし |

### 2.2 流れ

1. 参加者がライブ画面を開く → まなびのわのサーバーが **本人・参加者・配信中** を確かめてトークンを発行
2. ブラウザがトークンで SFU の部屋 `live-<id>` に入る（WebRTC・暗号化）
3. 話し手は声を送り（publish）、聞き手は受けるだけ（subscribe）
4. STT エージェントが話し手のトラックを1本ずつ購読 → トラックの持ち主（= トークンに書いた `users.id`）で `transcript_segments` に書く
5. ライブ終了 → サーバーが **部屋を消す**（全員切断）→ recorder が今までどおり動く

> ★ 誰の声かは「名前」ではなく **トークンに署名した `users.id`** で決まる。Teams の文字起こしを採らなかった理由（表示名しか無い）を ここで解消している。

## 3. 🛡️ セキュリティの壁

| # | 壁（何が起きたら困るか） | 越え方 |
|---|---|---|
| S1 | **なりすまし**（他人として入る・話す） | トークンは **サーバーだけが発行**。`identity = users.id`（`getUser` で確かめた本人）。ブラウザが名乗った ID は使わない |
| S2 | **部外者の入室** | 発行条件は「`live_participants` にいる」かつ「配信中」。部屋名は `live-<id>` に固定し、トークンにはその1部屋だけを書く（`roomJoin` + `room`） |
| S3 | **トークンの使い回し・持ち出し** | 有効期限は **10分**。切れる前にサーバーで再発行（その時点でまた参加者か確かめる）。ライブ終了で部屋ごと消すので古いトークンは入る先が無い |
| S4 | **聞き手が勝手に話す** | 聞き手は `canPublish: false`。話し手への昇格はサーバーが SFU の API で権限を変える（ブラウザ側では変えられない） |
| S5 | **盗聴**（通り道で聞かれる） | 音声は WebRTC の **DTLS-SRTP で必ず暗号化**。制御の通信は WSS（TLS）。TURN も TLS |
| S6 | **声が想定外の場所に出る** | SFU と STT を **§2.0 で決めた場所に自前で建てる**（🅰️私たちの国内クラウド／🅱️お客さんのテナント）。外部の通話サービスには渡さない。**録音機能（Egress）は使わない・音声は保存しない**。残るのは文字だけ |
| S7 | **鍵の漏れ** | `LIVEKIT_API_SECRET` と STT の鍵は **サーバーだけ**（`import 'server-only'`・`NEXT_PUBLIC_` を付けない）。Webhook は署名を検証してから受ける |
| S8 | **STT エージェントの偽書き込み** | エージェントは `transcript_segments` に書くだけの専用の口を使う。`user_id` は **トラックの持ち主（SFU がトークンから付けたもの）** からしか取らない。外部キーで参加者以外は弾かれる |
| S9 | **発言に仕込まれた命令** | 文字になった後は今と同じ経路なので、recorder の既存ガード（F10）がそのまま効く |
| S10 | **同意なしに声が文字になる** | 入室時に同意表示。マイクは既定でオフ。「文字になっています」を常に表示。**評価には使わない** を明記 |
| S11 | **使いすぎ・荒らし** | 1部屋の人数上限・同時の部屋数上限・トークン発行の回数制限・空の部屋は自動で閉じる。STT の月額上限をかける |
| S12 | **E2EE との両立** | 端末間暗号化（E2EE）にすると **サーバー側の STT が声を読めない**。今回の目的（知見を文字で残す）には STT が要るので、**E2EE ではなく「決めた場所から出さない」で守る**（どうしても社外に出せない会社は🅱️）。E2EE が必須の会社には「文字化を端末側でする」形に切り替える |

## 4. 🌐 ネットワークの壁

WebRTC は UDP を好む。企業ネットワークは UDP を止めがち。ここが一番の壁。
**「UDP → TCP → 443 の TLS」と順に降りていく道を用意しておき、どれかで必ずつながる** 形にする。

| # | 壁 | 越え方 |
|---|---|---|
| N1 | **UDP が止められている** | ICE over TCP（LiveKit の 7881/TCP）と **TURN over TLS（443/TCP）** に自動で降りる |
| N2 | **443 番しか出られない** | TURN を **443/TCP の TLS** で待ち受ける（専用のドメイン `turn.<社内ドメイン>` を割り当てる）。見た目は普通の HTTPS |
| N3 | **プロキシの TLS 復号（SSL インスペクション）** | 復号されると TURN の TLS が壊れる。**SFU と TURN のドメインだけ復号の対象外** にしてもらう（情シスへの依頼事項） |
| N4 | **許可したサイトにしか出られない（許可リスト）** | 必要なドメインは SFU と TURN の2つだけ（🅰️は私たちのドメイン／🅱️はお客さんが決めたドメイン）。**外部の通話サービスを使わないので それ以外は増えない** |
| N5 | **VPN で遠回り・遅延** | 全部 VPN を通す構成なら SFU を社内側に置く。分割トンネルなら SFU のドメインだけ直に出す。どちらかをお客さんの情シスと決める |
| N6 | **帯域** | 音声だけ・Opus で1本 **およそ 32kbps**。無音のときは送らない（DTX）。話し手は数人で 聞き手は受けるだけなので 1人あたり 100kbps 前後で収まる |
| N7 | **自宅・スマホ回線** | NAT の内側でも TURN で中継できる |

### 4.1 開けてもらうもの（お客さんの情シスへの依頼の雛形）

| 向き | ポート | 用途 | 必須 |
|---|---|---|---|
| 社員 → SFU | 443/TCP | 制御（WSS） | ✅ |
| 社員 → TURN | 443/TCP | TLS で中継（最後の砦） | ✅ |
| 社員 → SFU | 7881/TCP | ICE over TCP | あると速い |
| 社員 → SFU | 3478/UDP・50000–60000/UDP（または単一 UDP ポート） | UDP で直接 | あると最速 |

### 4.2 つながるまで確かめる（検証表）

| 環境 | UDP 直 | TCP | 443 TLS | 結果 |
|---|---|---|---|---|
| 本社の LAN | | | | |
| 支社・現場の LAN | | | | |
| 社外から VPN | | | | |
| 自宅 Wi-Fi | | | | |
| スマホ回線 | | | | |

- アプリに **接続テスト画面** を付ける（入る前にマイク・UDP・TCP・TURN を順に試して どの道で通ったかを出す）
- **どの行も最低「443 TLS」で通ること** を合格条件にする

## 5. 今あるもの と 足すもの

| 区分 | もの |
|---|---|
| ✅ そのまま使う | `transcript_segments`（`user_id` 付き）・recorder（タグ付け）・知見カード・RLS・`live_participants` の役割・ライブの開始／終了 API |
| ➕ 足す | トークン発行 API・Webhook 受け口・STT エージェント・SFU／TURN・ライブ開始で部屋を作り 終了で消す処理・接続テスト画面・環境変数（`LIVEKIT_URL` `LIVEKIT_API_KEY` `LIVEKIT_API_SECRET`） |
| 🔁 置き換える | デモの「ブラウザ音声入力 → segments API」は STT エージェントに置き換わる（書き込み先は同じ） |

## 6. 進め方

| 段階 | やること | 合格条件 |
|---|---|---|
| ① | 開発用に SFU を1台建て、トークン発行 API を作る | 話し手だけが話せる・聞き手は話せない・終了で全員切れる |
| ② | STT エージェントをつなぐ | 話し手ごとに正しい `user_id` で行が入る |
| ③ | 情シスと §4.1 を開け、§4.2 の検証表を埋める | 全環境で 443 TLS 以上で通る |
| ④ | 🅰️ 国内リージョンの本番へ出す／🅱️ お客さんのテナントに構築する。録音オフ・保存なしを確認 | 音声が決めた場所の外に出ないことを通信ログで確かめる |
| ⑤ | セキュリティ審査の回答集・データの流れの図を用意する | 🅰️を契約した日から使える状態 |

## 7. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| Teams の会議文字起こしを取り込む | 話者が **表示名** でしか返らず、`users.id` に結べない（名前で人を特定しない方針に反する） |
| 外部の通話サービス（他社の SaaS）をそのまま使う | 声が私たちでもお客さんでもない第三者のサーバーを通る。許可リストに外部ドメインが増える。🅰️は **私たちが自分で建てた SFU** なのでこれとは違う |
| 端末間暗号化（E2EE） | サーバーで文字にできない（§3 S12） |
| 会議室の共有マイク | 誰の声か分からなくなる（DESIGN.md §10） |

> **既知の壁には全部 越え方を当ててある。最後の「本当に通るか」は §4.2 の検証表を埋めて確かめる。** 穴がないふりはしない。
